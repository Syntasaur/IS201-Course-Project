# الخطة التأسيسية لمشروع IS201

> **الحالة:** ما قبل اختيار الفكرة. هذه خطة وهيكل عامان، وليسا مواصفات نهائية.
> لا تُنشأ جداول أو وظائف مجال العمل قبل اعتماد فكرة المشروع ومتطلباته.

## 1. الهدف من المرحلة الحالية

تجهيز قاعدة منظمة للعمل الجماعي وتحديد خطوات الانتقال من فكرة أولية إلى تطبيق
سطح مكتب قابل للعرض. لا تستهدف هذه المرحلة تنفيذ نظام لمجال محدد.

## 2. القرارات التقنية المبدئية

| الجزء | الاختيار المبدئي | ملاحظات |
|---|---|---|
| لغة البرمجة | Python 3 | تثبيت إصدار واحد متفق عليه بين أعضاء الفريق قبل التطوير |
| قاعدة البيانات | SQLite | مناسبة لتطبيق محلي صغير؛ تُصمم الجداول بعد تثبيت المتطلبات |
| واجهة Windows | Tkinter | خيار أولي مدمج مع Python؛ يُراجع إذا تطلب التصميم واجهة أغنى |
| الاختبارات | `unittest` أو `pytest` | اختيار الأداة عند بدء كتابة الاختبارات |
| إدارة الاعتمادات | `venv` و`requirements.txt` | تضاف الحزم الخارجية عند الحاجة فقط |

## 3. مراحل المشروع

### المرحلة 1 — اختيار الفكرة والتحقق منها

- حصر مشكلات واقعية يمكن حلها بتطبيق مكتبي.
- اختيار فكرة واحدة مناسبة للوقت والمقرر.
- تحديد المستفيدين والمشكلة الحالية والقيمة التي سيقدمها النظام.
- التأكد من إمكانية جمع بيانات تجريبية غير حساسة.
- كتابة وصف قصير للفكرة واعتماده من الفريق/المقرر.

**المخرج:** وصف فكرة معتمد وحدود واضحة لما سيبنيه المشروع.

### المرحلة 2 — جمع وتحليل المتطلبات

- تحديد أنواع المستخدمين وطريقة استخدامهم للنظام.
- كتابة قصص استخدام أو حالات استخدام للوظائف الأساسية.
- تصنيف المتطلبات إلى أساسية وإضافية.
- توثيق قواعد العمل والمدخلات والمخرجات ورسائل الأخطاء.
- تحديد النطاق المستبعد لتجنب توسع المشروع.

**المخرج:** قائمة متطلبات مرتبة حسب الأولوية ومعايير قبول لكل وظيفة أساسية.

### المرحلة 3 — تصميم النظام والبيانات

- رسم تدفق التنقل بين الشاشات ومخططات أولية للواجهة.
- تحديد الكيانات والعلاقات ورسم ERD.
- تحديد قيود البيانات ومفاتيحها وفهارسها المطلوبة.
- تقرير طريقة إنشاء قاعدة البيانات وترقيتها ومكان حفظها محليًا.
- مراجعة التصميم مقابل حالات الاستخدام قبل بدء التنفيذ.

**المخرج:** تصميم واجهة أولي ومخطط قاعدة بيانات معتمد.

### المرحلة 4 — بناء الهيكل والوظائف الأساسية

- إعداد بيئة Python افتراضية وطريقة تشغيل موحدة للفريق.
- تنفيذ طبقة الاتصال بقاعدة البيانات وتهيئتها بطريقة آمنة.
- تنفيذ النماذج والمستودعات (repositories) والخدمات وفق التصميم.
- بناء الشاشات وربطها بالخدمات دون وضع SQL داخل عناصر الواجهة.
- إضافة التحقق من المدخلات ومعالجة الأخطاء برسائل واضحة.

**المخرج:** نسخة أولية تحقق أهم حالة استخدام من البداية للنهاية.

### المرحلة 5 — الاختبار والتحسين

- اختبار قواعد العمل وعمليات قاعدة البيانات.
- اختبار حالات الإدخال الصحيح والخاطئ والبيانات الفارغة.
- التأكد من بقاء البيانات بعد إغلاق التطبيق وإعادة تشغيله.
- تجربة الواجهة على Windows والتحقق من سهولة الاستخدام.
- إصلاح العيوب وتحديث التوثيق عند تغيير السلوك.

**المخرج:** نسخة مستقرة اجتازت الاختبارات المحددة.

### المرحلة 6 — التجهيز والتسليم

- إعداد تعليمات التثبيت والتشغيل والنسخ الاحتياطي للبيانات.
- إعداد بيانات تجريبية خالية من المعلومات الشخصية الحقيقية.
- تجهيز عرض يشرح المشكلة والحل والتصميم والتنفيذ والاختبارات.
- مراجعة متطلبات تسليم المقرر وتوزيع أدوار العرض على الفريق.

**المخرج:** التطبيق والتوثيق والعرض النهائي.

## 5. مسؤولية كل جزء

- `ui/`: الشاشات، النوافذ، وعناصر التفاعل. لا يحتوي على استعلامات SQL.
- `services/`: قواعد العمل والتحقق من تتابع العمليات.
- `repositories/`: استعلامات SQLite وعمليات حفظ واسترجاع البيانات.
- `models/`: تمثيل الكيانات والبيانات بعد اعتماد مخططها.
- `database/`: فتح الاتصال، إنشاء المخطط، وإدارة تغييرات قاعدة البيانات.
- `utils/`: أدوات مشتركة صغيرة لا تنتمي لطبقة أخرى.
- `tests/`: اختبارات الخدمات والمستودعات والوظائف التي تحتاج تحققًا.
- `data/`: قواعد بيانات التطوير المحلية فقط؛ تُستثنى بيانات المستخدم من Git.
- `docs/`: الخطة والقرارات ومخططات التصميم ودليل الاستخدام عند توفرها.
- `scripts/`: أوامر مساعدة قابلة لإعادة الاستخدام، مثل تهيئة بيانات تجريبية.

## 6. قواعد تنظيم التنفيذ

- الواجهة تستدعي الخدمات، والخدمات تستخدم المستودعات، والمستودعات تتعامل مع
  قاعدة البيانات.
- استخدام معاملات SQLite للعمليات التي تتطلب حفظ أكثر من تغيير مترابط.
- استخدام الاستعلامات ذات المعاملات (parameters) بدل تركيب SQL من مدخلات المستخدم.
- إبقاء ملف قاعدة البيانات المحلية خارج التحكم بالإصدارات.
- عدم تخزين كلمات مرور أو بيانات شخصية حقيقية في بيانات العرض أو الاختبارات.
- إضافة الاعتمادات الخارجية إلى `requirements.txt` فقط عند اعتمادها.
- تسجيل القرارات المهمة وتحديث هذه الخطة إذا تغيرت التقنية أو حدود النطاق.

## 7. قرارات معلقة قبل بدء التنفيذ الفعلي

1. ما المشكلة أو المجال الذي سيعالجه التطبيق؟
2. من المستخدمون وما الوظائف الأساسية المطلوبة؟
3. هل Tkinter كافٍ للواجهة أم توجد متطلبات تستدعي مكتبة أخرى؟
4. هل التطبيق لمستخدم واحد على جهاز واحد؟ (هذا هو الافتراض المبدئي مع SQLite)
5. ما متطلبات المقرر الخاصة بالتوثيق والعرض والتسليم؟
6. ما إصدار Python وأداة الاختبارات التي سيستخدمها الفريق؟
